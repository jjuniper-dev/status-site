PATH is the enterprise AI control plane for HC/PHAC

PATH is not a single app, a data platform, or a lab. It is the governed operating layer that makes repeatable AI delivery possible across the enterprise through policy-enforced access, standardized deployment patterns, end-to-end auditability, and cost-attributed execution.

Primary role
Governed AI execution and control inheritance
Architectural stance
Control plane above multiple runtime implementations
Key boundary
Enterprise controls shared centrally, project execution isolated logically and financially

Why PATH exists

The problem is not that teams lack access to models. The problem is that AI patterns remain partial, cross-team dependent, difficult to operationalize end-to-end, and inconsistent in how they handle identity, ingress, audit, and cost management. PATH exists to convert fragmented experimentation into a repeatable enterprise capability.

Current-state issue

Partial delivery patterns

AI components may exist, but they do not arrive as a complete, deployable, inherited enterprise pattern. Teams assemble too much by hand.

Current-state issue

Unclear runtime governance

Model access, prompt logging, approvals, network controls, and telemetry can vary by initiative, creating review friction and weak defensibility.

Current-state issue

Cost and accountability gaps

Without a shared control model, AI consumption is harder to attribute, meter, budget, and govern at a project or branch level.

Core architecture model

PATH should be read as a layered operating model. The enterprise defines and enforces controls once, then projects inherit those controls through a standardized runtime pattern.

1. Enterprise control plane

Central governance, policy, gateway, observability, identity, and approval services. This is the layer that normalizes AI across the organization.

Microsoft Entra ID Azure API Management Azure Policy Microsoft Purview Azure Monitor / Log Analytics Microsoft Defender for Cloud Azure Cost Management

2. Project runtime plane

Dedicated or logically isolated project execution environments that consume enterprise controls rather than recreating them. Projects deploy AI capabilities here, but do so within inherited guardrails.

AI Foundry workspace / project Azure OpenAI access via APIM Azure AI Search for RAG Functions / Logic Apps / App Services ADLS Gen2 / project data stores Private endpoints / VNET integration

3. Reuse and platform services

Shared accelerators, templates, approved patterns, and reusable enterprise services that reduce duplication and improve consistency.

Shared model allow-list Prompt / policy templates Shared RAG patterns FinOps dashboards Approval workflows Reference architectures
Key principle: PATH is the control plane, not the only runtime. It governs and standardizes how AI runs. Different runtime implementations can exist beneath it, provided they inherit and comply with the enterprise control model.

Control responsibilities

What PATH centrally enforces

Identity and access: enterprise authentication, role boundaries, privileged access discipline, and traceable user or service identity.
Model gateway control: all model traffic routed through a governed enterprise gatekeeper to enforce policy, rate limits, token metering, and audit capture.
Telemetry and audit: standardized logging of prompts, responses, model IDs, timestamps, project IDs, policy version, and operational traces.
Compliance inheritance: reusable control baselines for privacy, security, architecture review, records defensibility, and location constraints.
FinOps: project-level cost attribution, budgeting, and consumption visibility.

What projects remain responsible for

Business purpose: clear use case scope, expected outcomes, human oversight design, and operational ownership.
Data readiness: lawful and appropriate data sourcing, curation, quality controls, and workload-specific access design.
Application logic: prompts, orchestration, retrieval patterns, user experience, workflow integration, and fallback paths.
Risk handling: workload-specific mitigations, testing, exception handling, and escalation design where decisions are sensitive.
Operational delivery: service support model, release discipline, backlog, and product lifecycle management.

Why the gateway matters

Azure API Management is the architectural choke point that gives PATH real control-plane authority. Without a single enterprise gateway, logging, rate control, policy enforcement, and model governance fragment quickly.

Gateway function

Policy enforcement

Central point to enforce approved model lists, request constraints, routing rules, and environment-specific controls.

Gateway function

Audit source of truth

Consistent prompt and response capture, token counts, and project attribution create a defensible audit trail across workloads.

Gateway function

Operational control

Shared throttling, key abstraction, usage quotas, and route management reduce duplication and simplify governance.

Isolation and cost attribution

PATH aims for shared enterprise controls with project-level execution separation. In practice, this means using logical or subscription-level isolation where needed to preserve security boundaries, operational clarity, and hard FinOps attribution.

Relationship to HAIL

HAIL and PATH are related, but they are not the same thing. HAIL is best understood as an operational runtime environment or landing zone pattern. PATH is the broader enterprise control model that should govern and standardize how such runtimes operate.

HAIL

Nature: operational platform / landing zone implementation.
Focus: enabling teams to build and run workloads.
Strength: tangible runtime delivery and experimentation support.
Risk if left alone: runtime capability without full enterprise control-plane convergence can remain local rather than institutionalized.

PATH

Nature: enterprise AI control plane and operating model.
Focus: shared governance, standardization, inheritance, and defensibility.
Strength: creates reusable enterprise conditions for safe scaling.
Target posture: multiple runtimes can align beneath PATH so the enterprise converges instead of fragmenting.

Decision-grade interpretation

Decision point

Do not define PATH as a tool bundle

That framing weakens architecture discipline. PATH must be positioned as the enterprise operating layer for governed AI.

Decision point

Keep the gateway central

If model access bypasses the enterprise gateway, PATH loses its ability to enforce controls consistently.

Decision point

Converge runtimes under one model

The enterprise should avoid parallel AI environments drifting into separate governance and operational regimes.

Bottom line

PATH is the operating system for enterprise AI at HC/PHAC.

It turns scattered AI capability into a governed enterprise service by separating shared control responsibilities from project execution, enforcing model access through a central gatekeeper, and making security, auditability, and cost attribution inheritable rather than repeatedly rebuilt.
